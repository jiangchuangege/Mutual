## 0. 评审信息与全局约定

### 0.1 产品一句话定义（评审基准，任何功能不得偏离）

TwoSpace 是**只属于两个人的私有共享空间**：把"生活协作（日历/待办/购物/记账）"、"关系维护（心情/感谢/纪念日/复盘）"、"经期关怀（本人授权制）"、"一起看电影（同步播放器控制）"、"关系成长与冲突修复"五件事，收进一个默认私密、默认不打扰的移动端容器里。

### 0.2 术语表（全文统一，评审时以此为准）

| 术语 | 定义 |
|---|---|
| 双人空间 / Space | 由 2 个账号组成的强隔离数据域，`spaceId` 为唯一隔离键，第三方账号无法进入 |
| 绑定 / Link | 两个账号建立 Space 的双向确认动作，一次仅允许一个 Space |
| 主控 / Leader | 电影院房间中当前有权发出播放/暂停/进度指令的一方，可转移 |
| 跟随 / Follower | 接收并校准到主控播放位置的一方 |
| 授权 / Consent | 数据所有者对"某项数据对伴侣可见"的显式、可撤回、可粒度化许可 |
| 四档可见 | 完全私密 / 仅关怀状态 / 预测日历可见 / 完全共享（见 3.5） |
| 脱敏 / Masking | 通知、锁屏、列表摘要中去除敏感词与敏感数值的展示策略 |
| 后置 | 本版保留功能定义，但不进入 MVP 与首年上线计划，需独立隐私评审 |
| 硬校准 | 播放位置偏差超过阈值时执行 seek 对齐，用户可见"已重新同步" |
| 软校准 | 通过微调播放速率在若干秒内追平偏差，用户无感 |

### 0.3 评级口径（本表所有打分的定义，避免评审时口径不一致）

- **使用频率**：高 = 每周 ≥4 天会打开；中 = 每周 1–3 次或事件驱动；低 = 每月 ≤1 次或一次性。
- **隐私风险**：低 = 泄露后仅尴尬；中 = 泄露后影响关系或社交评价；高 = 泄露后影响本人身心健康或财务；极高 = 涉及性/生殖/健康/人身安全，泄露可能造成实质伤害或法律合规风险。
- **开发复杂度**：低 = 单端 CRUD + 实时同步；中 = 多端状态一致 / 跨模块联动 / 第三方能力接入；高 = 音视频或高精度时序 / 复杂权限模型 / 强一致资金分摊。
- **实用度 / 情感价值**：1–5 分，5 为最高。实用度 = 减少现实摩擦；情感价值 = 提升关系感知。
- **MVP 优先级**：P0 = 首版必做；P1 = 首版后 3 个月内；P2 = 观察期后决策；`P2·后置`/`P2·需隐私评审`/`P2·不建议首版` 为 §0.5 强制标注。

### 0.4 十条设计原则 → 可执行规则（评审时按此逐条校验界面）

1. **实用优先**：任意一级页面必须能在 2 次点击内到达至少 1 个"减少现实摩擦"的功能（日历/待办/购物/记账）。
2. **轻量不打扰**：单用户每日主动推送 ≤3 条（不含用户自设提醒）；22:00–08:00 默认免打扰；任何提醒可"本周不再提醒"。
3. **默认私密**：所有新增数据字段的默认可见范围 = 本人；对伴侣可见必须是显式开关。
4. **经期必须本人授权**：经期相关数据在伴侣端的**任何**展示（含预测、含"关怀状态"）都必须由本人在授权页主动开启，默认关闭。
5. **不做医疗诊断**：所有健康页面底部固定常驻文案：「仅用于记录和陪伴，不构成医疗建议」。禁止使用"异常""确诊""风险高"等诊断性措辞，统一改为"建议就医检查"。
6. **不制造焦虑**：禁止倒计时式施压（除用户自建纪念日/见面倒计时）、禁止断签红点、禁止"TA 已 3 天没有…"类对比文案。
7. **不做排行榜**：任何形式的排名、亲密度排行、公开成就、公开比较一律不实现（含运营活动）。
8. **不做惩罚**：打卡断签不扣减、不清零宠物、不降亲密度、不发"你让 TA 失望了"类文案。
9. **不做监控**：位置、到家、社交报备一律默认关闭、需双方同意、可随时单方关闭、不提供轨迹回放与停留时长分析。
10. **删除即删除**：用户触发的删除在服务端执行物理删除 + 缓存失效 + 备份生命周期 ≤7 天，并在界面明示删除范围。

### 0.5 全局禁止项 → 反向验收规则（评审必须逐条确认"未实现"）

| 编号 | 禁止项 | 反向验收方式 |
|---|---|---|
| F-01 | 排行榜 / 亲密度排名 | 全局搜索 `rank`/`排行榜`，无相关接口与页面 |
| F-02 | 强制签到 / 断签惩罚 | 断签后 7 天回归，宠物状态不退化、无负向文案 |

| F-05 | 医疗诊断 | 健康文案经法务/医学顾问双签，词表禁用项通过 lint |
| F-06 | 默认共享经期 | 新装 + 绑定完成态下，伴侣端经期分区为"未授权"空态 |
| F-07 | 未经同意推送细节 | 抓包验证：未授权时服务端不下发任何经期字段 |

| F-12 | 过度装饰虚拟影院 | 影院场景元素 ≤6 个可交互点 |
| F-13 | 经期数据用于游戏惩罚 | 宠物/成就系统无经期字段入参 |

## 2. 情侣电影院专项（可施工级方案）

### 2.0 方案定位与法律立场（评审必读）

**采用"同步播放器控制"方案，不采用"同屏投流"方案。** 双方各自用自己合法持有的片源在各自设备上打开，TwoSpace 只同步 **play / pause / position / rate** 四种控制状态，并承载 **私密弹幕、表情反应、语音** 三条互动通道。

**平台责任边界（法律与合规立场）**：
1. App 内不存在任何片源内容、片源索引、片源搜索、片源跳转；
2. App 不接收、不暂存、不转发任何视频文件或视频流；
3. App 不接收、不转发、不录制片源音频（语音通话是"人声通话"，与片源音频完全无关）；
4. 片单中"平台"字段是**用户自填的文本标签**，不存 URL、不做跳转、不出现在任何联网请求中；
5. 片源由用户自备，同步失败/时长不一致由用户手动对齐（片源偏移），平台不做片源校验，也不承担片源一致性责任。

### 2.1 A. 同步技术流程（逐步骤，含系统行为）

#### 2.1.1 步骤 1：创建房间与邀请

#### 2.1.3 步骤 3：同步播放控制（核心）

**控制通道**：WebSocket（信令）＋ 客户端对时。所有状态变更**单一权威源 = 服务端会话对象的 `mediaState`**，避免双主控互相打架。

**数据结构**（`mediaState`，服务端持有）：
```
{ action: "play" | "pause" | "seek" | "rate",
  positionSec: 1234.5,        // 播放位置，保留 1 位小数
  rate: 1.0,                  // 播放速率
  leaderId: "u_A",
  seq: 1042,                  // 单调递增，用于丢弃乱序
  updatedAtServerMs: 1735..., // 服务端时间戳（权威时钟）
  mediaOffset: { A: 0, B: -2.5 }  // 各自片源偏移（秒） }
```

**对时（NTP 式，进入房间时 + 每 60 秒 + 每次重连）**：
1. 客户端发 `ping(t1)`，服务端立即回 `pong(t1, t2_server)`，客户端记 `t3`、`t4`；
2. 连采 5 次，取 **RTT 最小**的那一组计算时差：`offset = ((t2 - t1) + (t3 - t4)) / 2`；
3. `RTT > 400ms` 的样本丢弃，5 个样本全部失败则每 10 秒重试并提示"网络不稳定，同步精度会下降"；
4. 校准后的本地时钟估算：`serverNow ≈ localNow + offset`。

**跟随端位置推算**（每 500ms 重算一次）：
```
targetPos = mediaState.positionSec
          + (serverNow - mediaState.updatedAtServerMs) / 1000 * rate   // 仅在 action=play 时累加
localCanvasPos = 用户在本机播放器上的实际位置 + mediaOffset[me]
drift = localCanvasPos - targetPos
```

**漂移处理三档**（硬性阈值，禁止随意调整）：

| drift 绝对值 | 处理策略 | 用户可感知 |
|---|---|---|
| < 0.6 秒 | 忽略，不干预 | 无 |
| 0.6 – 1.5 秒 | **软校准**：把本机播放速率临时改为 `1.00 ± 0.05`（偏快用 1.05、偏慢用 0.95），最多持续 5 秒追平后恢复 1.0 | 无（但提示条显示"微调中"） |
| > 1.5 秒 | **硬校准**：立即 `seekTo(targetPos)`，浮条提示"已重新同步" | 有画面跳变 |

**硬校准防抖**：同一会话 30 秒内最多 1 次硬校准；超限则降级为软校准并把偏差阈值放宽到 2.5 秒，同时在房间底部显示"网络波动，同步精度下降至 ±2.5 秒"（诚实告知优于假装精确）。

**主控机制**：
- 进入房间默认 **A 为主控**（房主），界面显示"你为主控 · TA 跟随中"；
- 跟随方点击播放/暂停/进度条 → **不直接执行**，而是弹出"请求主控权限？"（双选：只发一次操作请求 / 申请接管主控）；
- 主控方收到"TA 想暂停"卡片 → 点「同意」→ 该次操作由主控代为发出（`action=pause`）；
- 「主控交给 TA」按钮可一键转移，转移后 UI 立即互换；
- 主控连续 45 秒无心跳 → 系统提示"连接异常，已把主控交给 TA"（避免主控卡死全房不动）。

**心跳**：主控每 **2000ms** 发一次 `heartbeat(mediaState)`（即使无状态变化，用于跟随端纠偏）；跟随端回 `ack(seq, drift)`；服务端记录最近 10 个 drift 样本用于质量上报。

**速率一致**：任一用户把播放器调到 1.25 倍速，必须点「我也调到 1.25」或由 App 提示"速率不一致，是否同步"，不一致时顶部显示"速率不一致（1.0 / 1.25）"黄条。

**为什么只承诺 ±1.5 秒**：因为真正的播放内核在用户自己打开的第三方播放器里，TwoSpace 只能控制"什么时候按播放/按到哪里"，无法读取播放器缓冲进度、无法控制解码起点、无法干预平台广告与片头。**帧级同步在物理上不可能**，对外任何物料不得使用"毫秒级同步""同屏观看"表述。

#### 2.1.4 步骤 4：语音通话（详见 2.5 时序）

房间内「语音」按钮 → 双方同意 → 接入成熟 RTC SDK → 独立音频通道，不影响同步信令。**不录音、不落盘、不转写**；房间结束即销毁频道与 token。

#### 2.1.5 步骤 5：私密弹幕与表情反应

| 项目 | 规则 |
|---|---|
| 可见范围 | 仅 `roomId` 内 2 个成员；服务端不写入任何公共流；不进任何推荐/广场 |
| 数据结构 | `{ roomId, senderId, text(≤24字), mediaPosSec, createdAt }` |
| 渲染绑定 | 弹幕按 `mediaPosSec` 锚定；跟随端在 `targetPos` 到达锚点 ±0.3 秒时渲染，因此**校准后弹幕仍对得上剧情** |
| 渲染区 | 固定高度带，**锁定在播放器字幕安全区之上**（屏幕高度 62%–74% 区间），最多同屏 3 条，单行 24 字，固定 8 秒匀速滚过，无颜色/无特效/无变速 |
| 开关 | 任一方可单独关闭"看弹幕"，关闭仅本地不渲染，不影响对方 |
| 敏感内容 | 文本走本地关键词兜底 ＋ 服务端审核队列（仅告警不拦截，因为内容不公开） |
| 表情反应 | 4 选：笑哭/害怕/嗑到了/需要抱抱；点击即飘 1 个气泡（1.5 秒消失），限流 1 次/2 秒，不遮挡字幕安全区 |
| 生命周期 | 房间进入 `S9_ENDED` 后弹幕与表情在服务端 24 小时内物理删除，不入回忆卡 |

#### 2.1.6 步骤 6：结束与回忆卡

1. 任一方点「结束观影」→ 双方收确认弹层（"TA 想结束这次观影"）→ 双方确认或任一方选择"我还想看完"（不强制，仅提示）；
2. 服务端 `state=S9_ENDED`，立即：停心跳、吊销 RTC token、销毁音频频道、关闭弹幕通道；
3. 双方进入 `S10_RECAP` 回忆卡页：片名、日期、时长（按 `ENDED - COUNTDOWN_END` 计算）、**双方各自评分（1–5 星）**、一句短评（≤50 字）、手动上传截图（≤3 张，单张 ≤5MB，客户端压缩后上传）；
4. **不做自动截屏/录屏**（版权与隐私双风险），截图必须用户手动选择；
5. 双方都点「保存到回忆」后才写入 4.9 时间轴；任一方不保存则仅在 `roomId` 会话记录中保留 7 天后删除；
6. 若结束后 10 分钟无人操作，自动保存为"仅我可见"的草稿。

#### 2.1.7 步骤 7：断线重连（详见 2.6）

掉线 → 对方看到"TA 暂时掉线" → 重连 → 拉快照 → 对时 → 校准 → 提示"已重新同步" → 继续观影；超时转"等待中"，可重新邀请。

### 2.4 D. 邀请功能规格

| 项目 | 规格 |
|---|---|
| 码格式 | 6 位纯数字；服务端以 `HMAC-SHA256(code, roomSalt)` 存储，不存明文 |
| 码强度与防爆破 | 每账号 10 次/小时错误上限，超限锁定 1 小时；每 IP 5 次/分钟；错误码与"房间不存在"统一返回同一文案，避免枚举 |
| 链接 | `https://tws.app/j/<token>`，token 为 22 位不透明串，**不含片名、不含 spaceId 明文、不含用户 ID** |
| 扫码 | 二维码内容为同一 token 链接；扫码后若未装 App 落地页仅显示"XXX 邀请你一起看电影"（XXX 为昵称，可在设置里改为"有人"） |
| 有效期 | **默认 30 分钟**；可「延长 30 分钟」一次（最多到 60 分钟）；到期即失效 |
| 重新生成 | 可无限次；每次生成 `codeVersion+1`，**旧码与旧 token 立即失效**，旧链接打开显示"邀请码无效或已过期" |
| 人数 | 严格 2 人；第 3 次占位失败返回 `ROOM_FULL` |
| 被邀请方确认 | 必须点「加入房间」；不接受"静默加入"；确认页不显示片名 |
| 迟到生效 | 房间已进入 S3 之后，旧码不再可用，须由房主「重新邀请」生成新码（防止中途有人插入会话） |
| 邀请失败文案（唯一口径） | ①「邀请码无效或已过期」②「房间已满」③「房间已结束」④「TA 已经在房间里了」⑤「网络不太好，重试一次」 |
| 通知 | 房主侧：`room_invite_created / peer_joined / peer_declined / invite_expired`；被邀请侧仅 1 条 `room_invite`；全部脱敏，不含片名 |

### 2.5 E. 语音通话时序

#### 2.5.1 正常时序（时序图文字版）

```
[A 端]                          [服务端]                          [B 端]
 1 点「语音」──voice_invite──────▶ 校验房间状态=S5/S6
 2                                ──push(脱敏)──▶ 弹层"TA 想和你语音"
 3                                                  ◀── 60 秒内选择
 4                               ◀─voice_accept─── B 点「同意」
 5  ◀──voice_ready(tokenA)──── 签发 RTC token（TTL 15min，绑定 roomId+uid）
 6                                ──tokenB──▶
 7  两端 join RTC channel(roomId)（音频独立通道，与同步信令互不阻塞）
 8  状态条"语音已接通 · 不录音"；双方均出现：静音 / 扬声器·听筒 / 独立音量滑杆
 9  …… 观影同步继续（控制信令与音频通道完全分离）……
10  任一方点「关闭语音」→ leave channel → 双方状态条变"语音已结束"
11  房间结束/解散 → 服务端吊销 token、销毁频道、删除映射（无任何音频落盘）
```

#### 2.5.2 分支与时序契约

| # | 分支 | 时序契约与界面 |
|---|---|---|
| E1 | B 60 秒未响应 | 自动视为拒绝，A 端提示"TA 可能不方便，稍后再试"；同一方 10 分钟内再次邀请间隔 ≥60 秒 |
| E2 | B 拒绝 | A 端"TA 现在不方便语音"；**不显示拒绝次数、不累计** |
| E3 | 权限未授予（麦克风） | 本端弹系统授权；拒绝则提示"没有麦克风权限，只能文字互动"，通话不发起 |
| E4 | token 签发失败/过期 | 自动重签 1 次；仍失败 → "语音暂时用不了，可以先用文字" |
| E5 | 加入频道失败 | 3 秒重试 2 次，仍失败降级文字模式，同步播放不受影响 |
| E6 | 弱网判定 | `RTT>400ms` 或 `丢包>10%` 或 `jitter>60ms` 持续 10 秒 → 顶部黄条"网络较弱，建议切换为仅文字互动"＋一键「切换为文字」 |
| E7 | 切换为仅文字 | 立即 leave channel、关闭语音 UI，保留弹幕/表情；**不会自动恢复语音**，需重新走 E 全流程 |
| E8 | 一方掉线 | 语音通道随之断开，界面对另一方显示"语音已中断"；重连后**不自动开启语音**，需重新确认（防止在对方不知情时收音） |
| E9 | 房间解散/结束 | 服务端强制 `leave` 所有成员并吊销 token；客户端关闭麦克风采集 |
| E10 | 后台/来电 | App 进入后台或系统来电，默认**关闭麦克风上行**（不做通话中录制），回前台需点「恢复语音」 |

#### 2.5.3 RTC SDK 选型与硬性配置（首版不自研）

| 项目 | 要求 |
|---|---|
| 选型 | 声网 Agora / 腾讯 TRTC / ZEGO 三者择一（建议按"双人 1v1 音频 + token 鉴权 + 关闭录制能力 + 弱网指标回调"打分，POC 后定） |
| 频道模型 | 1v1，`channelName = roomId`（服务端不可预测的 UUID） |
| 鉴权 | 服务端签发短期 token（TTL 15 分钟），与 `roomId+uid` 绑定，禁止 App 内置永久密钥 |
| 录制 | **关闭云端录制、关闭本地录制、关闭音频转写、关闭内容审核上传** |
| 音频路由 | 支持听筒/扬声器/蓝牙切换；独立音量滑杆只调"对方人声"，不改系统媒体音量（避免盖住片源声音） |
| 回声消除 | 开启 AEC/ANS/AGC；提示用户佩戴耳机可显著降低回声 |
| 指标 | 订阅 `RTT / 丢包率 / jitter / 卡顿率`，写入房间质量日志（不含音频内容） |
| 成本口径 | 2 小时/次、2 人；按月活 10 万、人均 8 次/月估算，需在评审时确认 RTC 预算与降级策略（超预算时按比例关闭语音入口，不静默降质） |
| 禁止 | 自研 RTC、自建 SFU、自研回声消除 |

### 2.6 F. 断线重连

#### 2.6.1 检测机制

| 层 | 检测方式 | 判定时间 | 用户可见 |
|---|---|---|---|
| 客户端网络 | 系统网络回调 + WebSocket `onclose` | 立即 | 顶部灰条"网络已断开" |
| 心跳 | 客户端 10 秒 `ping`；服务端 30 秒收不到 `pong` 判离线 | ≤30 秒 | 对方端"TA 暂时掉线" |
| 主控心跳 | 主控 2 秒一次 `heartbeat`；45 秒缺失 | ≤45 秒 | 自动转移主控 |
| 应用存活 | App 进程被杀死 | 服务端即时感知 WS 断 | 同 S7 |

#### 2.6.2 重连协议（客户端）

1. 指数退避重连：`0.5s / 1s / 2s / 4s / 8s`，单轮最多 8 次（合计约 63 秒），失败进入下一轮并显示「正在重新连接…（第 N 次）」；
2. 重连成功第一步：`GET /room/{roomId}/snapshot`，返回
   `{ roomState, mediaState:{action, positionSec, rate, seq, updatedAtServerMs}, leaderId, mediaOffset, peerOnline, voiceEnabled }`；
3. 第二步：重新执行 5 次 ping 对时（见 2.1.3），更新 `offset`；
4. 第三步：按 `targetPos` 计算 drift 并校准（若 drift > 1.5 秒走硬校准），成功后浮条「已重新同步」并上报 `resync_success`；
5. 第四步：同步弹幕锚点（拉取 `mediaPosSec` 在 `[targetPos-30, targetPos+30]` 区间内未读弹幕）；
6. **语音不自动恢复**：若房间此前有语音，界面显示"语音已断开，需要重新开启"＋「重新开启语音」按钮，需对方再次同意。

#### 2.6.3 时间轴与用户文案（唯一口径）

| 时间 | 掉线方界面 | 在线方界面 | 系统行为 |
|---|---|---|---|
| 0–10 秒 | 顶部"网络已断开，正在重连…" | 无感（继续本地播放到当前缓存） | 保留会话 5 分钟、保留 token 不吊销 |
| 10–30 秒 | 同 上 | 状态条"TA 暂时掉线" | 暂停主控转移，记录 `drift` |
| 30 秒–5 分钟 | "正在重新连接…（第 N 次）" | "TA 暂时掉线，正在重连…"，可「继续等」或「结束」 | 房间保持 S7 |
| 5 分钟 | "连接失败"＋「重试」 | "TA 已离线 5 分钟"＋三按钮：继续等待 / 重新邀请 / 结束并保存回忆卡 | 房间进入 S8，停播，发脱敏推送 |
| 5–30 分钟 | 可反复重试 | 只能等待/重新邀请/结束 | S8 保持 |
| 30 分钟 | 房间已关闭 | 同 | 自动 S9，保存草稿，销毁 token/频道 |

#### 2.6.4 重新邀请的特殊规则

- S8 中「重新邀请」会生成**新码**，`codeVersion+1`，旧码失效；
- 对方用新码加入后**不重建房间**，沿用原 `roomId` 与原回忆卡草稿；
- 重新加入后必须重新走"片源准备→就位→倒计时"，不直接跳回 PLAYING（避免双方片源位置错位）。

### 2.7 同步精度测试与验收方法（研发必须交付证据）

| 测试项 | 方法 | 通过标准 |
|---|---|---|
| 基础同步 | 双机同一片源，执行 20 次 play/pause/seek 混合操作，记录每次 drift | P90 `|drift| ≤ 1.5s`，均值 ≤ 0.8s |

## 4. 信息架构

### 4.1 导航总原则

1. **一级导航只有 5 个 Tab，且一级命名不含任何敏感词**（不出现"经期""生理期"字样，统一收纳在「关怀」下），避免他人瞥见屏幕即产生推断。
2. 每个 Tab 首屏即为可用页，不做纯目录页；Tab 内二级用顶部胶囊分段控件，三级才进详情页。
3. 全局右上角常驻「双人头像」= 当前 Space 状态（在线/离线/掉线中），点击进入 Space 信息页。
4. 全局右下角悬浮「＋」按上下文变化：今天页=新建待办、生活页=新建、关怀页=记录、影院页=一起看电影。
5. 不做全局搜索（首版）；搜索仅在日历、片单、清单库内局部提供。
6. 深链规则：`tws://room/<roomId>`、`tws://j/<token>`、`tws://space/join/<code>`；落地页一律不含片名与敏感数据。

## 8. MVP 验收标准

### 8.1 验收环境与方法

- 环境：TestFlight / 内测包 + 预发布服务端 + 抓包工具（Charles/mitmproxy）+ 双机（iOS + Android 各一）。
- 角色：产品（验收主责）、研发（联调）、测试（用例）、隐私安全（专项）、法务（文案）。
- 通过门槛：**A 类（功能）全部通过；B 类（隐私安全）全部通过且不可豁免；C 类（性能）达到阈值；D 类（文案视觉）无 P0/P1 问题。**

### 8.6 上线门槛（Go / No-Go 一票否决项）

1. AC-B01、AC-B02、AC-B03、AC-B07、AC-B08 任一不通过 → **不允许上线**。
2. 法务对《用户协议》《隐私政策》《健康免责声明》《儿童与未成年人说明》四份文件签署。
3. 应用商店隐私清单（含 RTC SDK、推送 SDK、统计 SDK）与实际行为一致。
4. 客服话术手册（含"如何撤回授权""如何解绑""如何处理泄露申诉"）交付。
5. 数据删除 SOP 与演练记录（含备份清理）完成。
6. 灰度策略：1% → 5% → 20% → 全量；每阶段观察崩溃率、同步精度、隐私投诉率。

### 8.7 MVP 指标验收（做什么算成功）

| 指标 | 定义 | 目标 |
|---|---|---|
| 绑定完成率 | 注册后 7 天内完成双向绑定 / 注册数 | ≥45% |
| 双人周活跃（WAU2） | 双方在 7 天内各有 ≥3 天活跃 / 已绑定对数 | ≥35% |

| 隐私投诉率 | 隐私相关投诉 / 活跃用户 | <0.05% |
| **反指标（出现即视为设计失败）** | 因"被监视感"导致的解绑或关闭授权 | 需专项监控，连续两周上升即触发复盘 |

### 9.2 数据留存与删除矩阵

| 数据类别 | 主库留存 | 备份留存 | 用户可删 | 删除方式 | 说明 |
|---|---|---|---|---|---|
| 经期/症状/情绪/备注 | 至用户删除或注销 | ≤7 天 | 是（单条/全部） | 物理删除（软删 24h 可恢复） | 加密字段随记录一起删除 |
| 备孕/避孕记录 | 至用户删除或注销 | ≤7 天 | 是 | 物理删除，无恢复 | 独立加密域 |
| 心情天气 | 365 天滚动 | ≤7 天 | 是 | 物理删除 | 过期自动清理 |
| 待办/购物/日历 | 至用户删除或解绑 | ≤7 天 | 是 | 物理删除 | 已完成为 30 天归档 |
| 账本流水 | 至用户删除或解绑 | ≤7 天 | 是（单笔） | 物理删除 | 不做财务凭证用途 |
| 感谢卡/夸夸卡/日记 | 至用户删除或解绑 | ≤7 天 | 是 | 物理删除 | 日记**写入后不可撤回**，删除即双方都看不到 |
| 观影片单/回忆卡 | 至用户删除或解绑 | ≤7 天 | 是 | 物理删除（含图片对象存储） | 图片需同步删除 CDN 缓存 |
| 房间弹幕/表情 | ≤24 小时 | 无 | 是 | 物理删除 | 不进入任何持久存储 |
| 语音 | **不存储** | 无 | — | 不适用 | 仅内存通道，房间结束销毁 |
| 位置（单次授权） | ≤2 小时 | 无 | 是 | 到期即删 | 不写历史表 |
| 审计/授权记录 | 180 天 | ≤7 天 | 否（合规保留） | 到期自动清理 | 仅记录"谁/何时/改了什么档位"，不记录内容 |
| 崩溃与性能日志 | 90 天 | — | 否 | 到期清理 | 不含业务内容与敏感字段 |

### 9.3 评审待决问题（现场必须给出结论，逐条留档）

| ID | 问题 | 选项 | 建议 | 影响 |

| P-01 | 电影院是否进入 MVP（§3.4 M8） | A 进 MVP（14 周内需 2 名客户端 + 1 名服务端专职）／B 降至 v1.1，MVP 为 8 项 | **A**，但设置 Go/No-Go 门：第 6 周同步精度 POC 未达 P90 ≤1.5s 则自动降级为 B | 决定首版是否有差异化卖点；决定排期与人力 |

| P-05 | 关系健康自评（7.7）是否永不互看 | A 永不互看（接口不返回）／B 可主动共享 | **A** | 若选 B，需重做隐私评审 |

| P-08 | RTC 供应商选型 | 声网／TRTC／ZEGO | 两周 POC 后按"1v1 音频质量 + 关闭录制能力 + 成本"定 | 影响成本与合规声明 |

| P-10 | 年度报告是否做分享（图片） | A 不分享，仅双方可见／B 生成图片需二次确认且默认脱敏 | **B**（默认脱敏：不含金额、不含症状、不含片名以外隐私） | 与 F-03 禁止项"公开影院成就"边界相关 |
